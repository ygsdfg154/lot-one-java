# lot-one 物联网平台上线切换方案

## 1. 概述

本文档描述 lot-one 物联网平台从 Go/Rust 版本切换到 Java 版本的完整上线方案，包括上线前检查、数据迁移、灰度发布、回滚和监控告警。

### 1.1 切换目标
- 零数据丢失
- 最小化业务中断（< 5分钟）
- 可随时回滚
- 全链路可观测

### 1.2 切换范围
| 模块 | 旧版本(Go/Rust) | 新版本(Java) | 端口 |
|------|-----------------|-------------|------|
| 管理后台 | admin-console | lot-one-admin | 8081 |
| App后端 | device-app | lot-one-device | 8082 |
| API网关 | api-gateway | lot-one-gateway | 8083 |
| 设备网关 | iot-gateway | lot-one-iot-gateway | 8084/8083 |
| 数据处理 | iot-worker | lot-one-iot-worker | 8085 |
| 查询API | query-api | lot-one-query-api | 8086 |

## 3. 数据迁移方案

### 3.1 迁移策略
采用**双写+增量同步**策略：
1. 先启动 Java 版本服务（不接入流量）
2. 配置双写：旧版本写入数据时同时写入新版本
3. 全量迁移历史数据
4. 校验数据一致性
5. 切换流量到新版本
6. 观察稳定后关闭旧版本

### 3.2 MySQL 数据迁移
```bash
# 导出旧版本数据
mysqldump -h old_host -u root -p lot > lot_backup.sql

# 导入到新版本
mysql -h new_host -u root -p lot < lot_backup.sql

# 校验数据一致性
mysqldump --no-data --skip-comments lot > schema_new.sql
diff schema_old.sql schema_new.sql
```

### 3.3 MongoDB 数据迁移
```bash
# 导出旧版本数据
mongodump --host old_host --db lot --out /tmp/mongo_backup

# 导入到新版本
mongorestore --host new_host --db lot /tmp/mongo_backup/lot

# 校验数据量
mongo --host old_host --eval "db.device_status.count()" lot
mongo --host new_host --eval "db.device_status.count()" lot
```

### 3.4 TDengine 数据迁移
```sql
-- 导出旧版本数据
taos -s "SELECT * INTO OUTFILE '/tmp/tdengine_backup.csv' FROM lot.device_telemetry"

-- 导入到新版本（需要先创建超级表）
taos -s "INSERT INTO lot.device_telemetry USING lot.device_telemetry TAGS ('device_id') VALUES (...)"

-- 或使用 taosdump 工具
taosdump -D lot -o /tmp/tdengine_backup
taosdump -i /tmp/tdengine_backup
```

### 3.5 Redis 数据迁移
```bash
# 全量同步（推荐）
redis-cli -h old_host --rdb /tmp/redis_backup.rdb
redis-cli -h new_host --pipe < /tmp/redis_backup.rdb

# 或使用 redis-shake 工具增量同步
```

### 3.6 数据一致性校验
```sql
-- MySQL 表行数对比
SELECT COUNT(*) FROM lot_device;
SELECT COUNT(*) FROM lot_order;

-- MongoDB 集合文档数对比
db.device_status.count()
db.alarm_event.count()

-- TDengine 数据量对比
SELECT COUNT(*) FROM lot.device_telemetry;
```

## 4. 灰度发布方案

### 4.1 灰度策略
采用**按设备灰度**策略：
1. 第一阶段：内部测试设备（10台）
2. 第二阶段：1% 设备（约100台）
3. 第三阶段：10% 设备（约1000台）
4. 第四阶段：50% 设备
5. 第五阶段：100% 设备

### 4.2 灰度配置
在 Nacos 配置中心配置灰度规则：
```yaml
gray:
  enabled: true
  strategy: device_id
  whitelist:
    - TEST000001
    - TEST000002
  percentage: 1  # 灰度百分比
  newVersion: java-v1.0.0
  oldVersion: go-v2.5.0
```

### 4.3 流量切换
使用 Nginx / API 网关进行流量切换：
```nginx
upstream iot_gateway {
    server old_gateway:8083 weight=90;
    server new_gateway:8083 weight=10;
}
```

### 4.4 灰度观察指标
每个灰度阶段至少观察 24 小时，关注以下指标：
- 设备连接成功率（目标 > 99.9%）
- 消息处理延迟（目标 < 100ms）
- 数据写入成功率（目标 > 99.99%）
- 报警触发准确率（目标 > 99%）
- 服务CPU/内存使用率（目标 < 70%）
- 错误日志数量（目标 < 10条/小时）

## 5. 回滚方案

### 5.1 回滚触发条件
出现以下任一情况立即回滚：
- 设备连接成功率 < 95%
- 消息处理延迟 > 1秒
- 数据丢失 > 0.1%
- 服务CPU/内存 > 90% 持续5分钟
- 核心业务不可用 > 5分钟
- 出现严重安全漏洞

### 5.2 回滚步骤
1. **立即停止流量切换**：将流量全部切回旧版本
2. **停止新版本服务**：关闭 Java 版本所有服务
3. **数据回滚**：
   - MySQL：使用切换前的备份恢复
   - MongoDB：使用切换前的备份恢复
   - TDengine：切换期间的数据通过双写已同步到旧版本
   - Redis：切换期间的数据通过双写已同步到旧版本
4. **验证旧版本服务**：确认旧版本所有功能正常
5. **通知相关人员**：发送回滚通知，说明回滚原因

### 5.3 回滚时间预估
- 流量切换：< 1分钟
- 服务停止：< 2分钟
- 数据回滚：< 30分钟（取决于数据量）
- 服务验证：< 5分钟
- **总回滚时间：< 40分钟**

### 5.4 回滚后处理
- 收集新版本错误日志
- 分析问题根因
- 修复问题后重新准备上线
- 编写事故报告
